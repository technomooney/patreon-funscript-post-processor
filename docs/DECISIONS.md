# Decisions log (append-only; newest last)

Each entry: what problem, what was decided, what was rejected, how to verify. Written so a later session knows *why*.

## 2026-10-17 - Shared per-library SQLite store
- **Problem:** the user transcodes with the AV1 compressor (`../Av1LibraryCompression`) and also pulls pixeldrain repos with a manual `rclone copy`; rclone compares name/size so transcoded files (.mkv->.mp4, smaller) look missing and get re-fetched. Separately, history was thousands of `.folder_log.json` files, and the compressor's `folder_log.use_root()` *moved* those away, silently erasing the downloader's history. The two tools could not read each other's records.
- **Decision:** one SQLite DB per library root (`.library-data/library.db`) shared by both tools via an identical `library_db.py`; machine-local data goes to user storage (`app_paths`). File identity (`files` table) survives renames/recompression, so downloads key on pixeldrain link id, not name/size. See `docs/LIBRARY_DB.md`.
- **Rejected:** JSON/JSONL manifests (no cross-queries, no cross-process safety); keeping data in the repo dir (tied to one checkout); committing library data to git (libraries are not repos).
- **Verify:** `python -m unittest discover -s tests -v`.
- **Plan:** `~/.claude/plans/ive-got-an-issue-zazzy-star.md` (parts 1-7: wrappers, standalone migration script, pixeldrain sync, global base64 decoding, Discord full history, drift detection, verified rebuild).

## 2026-10-17 - App-level data moves from the repo dir to user storage
- **Problem:** creator profiles (`.creators.json`), password history (`.creator_data.db`), the undo pointer, and the logged-in Discord/JOIGang browser profiles all sat in the repo directory (gitignored). That ties them to one checkout, and a second tool (the AV1 compressor, future tools) could never share them.
- **Decision:** they live under `app_paths.app_home()` (`~/.local/share/library-tools`, `%LOCALAPPDATA%\library-tools`, or `$LIBRARY_TOOLS_HOME`). Profiles and passwords are tables in `app.db` (`app_db.py`; creator_db adds its tables to the same file); the pointer is a file there; browser profiles are `profiles/<name>/`. Old files are COPIED in on first use (`legacy_app_data.py`: INSERT OR IGNORE for passwords, copy-if-missing for files/profiles, Chromium `Singleton*` locks skipped) and are never moved or deleted -- the user can remove them once satisfied. `CREATOR_DB_PATH` / `ACTION_LOG_POINTER_PATH` overrides still work for tests.
- **Rejected:** moving (loses the rollback path if the new location misbehaves); a separate DB file for passwords (one app DB is simpler to back up and inspect); putting app data inside libraries (it is per-machine, not per-library).
- **Prod note:** the live copy at `/media/Software/StandaloneSoftware/patreondownloaderpostprocessing` has its own repo-root data; after syncing, the first run there copies it into the user's app home.
- **Verify:** `python3 -I -m unittest discover -s tests -v` (`tests/test_app_data.py`).

## 2026-10-17 - Base64-hidden links are decoded globally
- **Problem:** at least one creator posts pixeldrain links as base64 text (in Discord, possibly posts too). Nothing in the repo decoded base64, and the rule from the user is that this is a core feature, not a per-creator hack.
- **Decision:** `link_decoder.py` (stdlib) plus a hook in `downloadContent._walk_description`, which every description/link-extraction path (including the Pize plugin) already goes through. Decoded entries are tagged `decoded_from_base64`. A candidate counts only if it is >=24 base64 chars, decodes to strict UTF-8 with no control chars, contains a URL (or `host.tld/path`) within 2 decode layers, and the URL's domain is supported (`check_domain`). Already-visible URLs are blanked out before scanning so path segments are never mistaken for base64.
- **Rejected:** per-creator decoding in plugins (every future creator would need it re-added); accepting any decoded URL (random long words and unknown domains would create "unknown domain" noise); shorter minimum length (more false positives).
- **Not covered yet:** base64 inside a link's href or split across formatted runs; hex/rot13/reversed encodings. Discord messages go through the same decoder once the Discord history reader lands.
- **Verify:** `tests/test_link_decoder.py` (stdlib) and `tests/test_description_base64.py` (needs the project venv).

## 2026-10-17 - Discord full-history reader
- **Problem:** `discord_passwords._load_channel_messages` only sees the few dozen messages Discord has rendered, so an older archive's password (or an old base64-encoded pixeldrain link) could never be found. It also returned plain text only: no message ids, timestamps, authors, or hrefs.
- **Decision:** `discord_history.py` scrolls the channel up (Discord's list is virtualized, so each pass merges what is currently rendered by snowflake id) until the channel start, a previously processed message (`since_message_id`), or a cap. Termination is by stall detection (N scrolls with nothing new) because the "start of channel" banner is locale-dependent. Messages are stored in the library DB `discord_messages` table (`save_messages` / `newest_stored_id` / `mark_processed`) so later scans are incremental. `fetch_password_history_full` scans the whole chat for passwords. Browser-only, manual login, no token -- unchanged from the earlier deliberate decision.
- **Refactor:** `discord_passwords.open_channel()` (config, login, navigation) and `passwords_from_texts()` were split out so both readers share them; behaviour of the old functions is unchanged.
- **Not verified live:** the DOM selectors (`li[id^="chat-messages-"]`, `message-content-`, `message-username-`, `time[datetime]`) follow Discord's current markup but could not be exercised without the user's logged-in profile. `python scripts/discord_history.py <creator> --max 50` is a read-only dry run to check them; expect one selector-tweak round if Discord changed its markup.
- **Verify:** `tests/test_discord_history.py` covers the scroll/collect loop (virtualized fake channel, since-id, caps, stall) and the DB bookkeeping.

## 2026-10-17 - Generic pixeldrain repo sync replaces the manual rclone copy
- **Problem:** `rclone copy` decides what is missing by file name/size. After the AV1 compressor transcodes a file (smaller, sometimes .mkv -> .mp4, original moved to `.trash`), rclone sees it as missing/different and downloads the original again, undoing the space savings. Neither repo contains rclone; the user ran it by hand.
- **Decision:** `scripts/creator_scripts/pixeldrain_repo_sync.py` (+ `pixeldrain_util.py`) lists the saved pixeldrain `/l/` list(s) / `/u/` files via the API (which returns id, name, size, sha256) and classifies each remote file: **have** (id recorded done / in `files` / same sha256 / same original name+size / on disk with same size / the compressor's `compress_library` record with `status='compressed'` and matching `original_size`), **ambiguous** (same name, different size or extension; compressor record with non-matching size) and **new**. Only **new** is downloaded (scratch folder, sha256 verified, then moved in; never overwrites). **Ambiguous is reported and left alone**: it could be the user's own edited/transcoded copy, and the failure we are avoiding is re-fetching, so the safe default is not to act. Outcomes go into the shared `pixeldrain_links` / `files` tables as they happen (resumable) and downloads are journaled (`create_marker`) for undo. Dry-run plan is printed and confirmed before anything downloads.
- **Why recognition does not need migration first:** the compressor's own log (including its old `library_log.jsonl`) is read through `folder_log.read()`, so libraries already transcoded before this existed are recognised on the first run, and the run then records them (`_adopt`) so the next run needs no inference.
- **Library root:** if no `.library-data` exists above the creator folder the plugin refuses when unattended and asks when interactive. Silently creating one would nest a second database under the real library root and shadow it (nearest root wins). `migrate_library_data.py` is meant to declare roots up front.
- **Not done / limits:** `/d/` filesystem shares are not listed (API shape unverified); Pize still uses its own JSON manifest (moving it onto the shared tables is a separate step); the compressor does not yet write `files` rows on replace (it is recognised through its log until it does); not exercised against the live pixeldrain API (network is faked in tests).
- **Verify:** `tests/test_pixeldrain_repo_sync.py` (includes the transcoded-not-redownloaded case and the compressor-log-only case).

## 2026-10-17 - Discord channel -> pixeldrain links plugin (generic, per creator)
- **Problem:** a creator shares content as pixeldrain links in a Discord channel, base64-encoded. Needs automated, repeatable downloads that don't re-fetch what the user already has or has transcoded.
- **Decision:** `creator_scripts/discord_pixeldrain_links.py` is deliberately creator-agnostic (creator = the folder name; channel config via the existing `creator_profiles` Discord setup). First run reads the whole channel history, later runs only newer messages (`discord_messages` table, `since_message_id`). Hidden links are decoded when a message is *saved* (from the full text including spoilers, which isn't stored) and kept in `decoded_links_json`; visible hyperlinks come from stored hrefs. All pixeldrain `/l/` and `/u/` links go to the shared `pixeldrain_sync` engine, so ownership/transcode recognition is identical to the repo-sync plugin. A message is marked processed only if every link synced without a failure or unreadable source; otherwise it is retried next run. Files go to a configurable subfolder (default `discord`) so they don't mix into the post folders. Interactive runs default to a dry run first.
- **Rejected:** a plugin hard-coded to one creator (the user said base64 and Discord handling should be global, and the creator wasn't named); marking messages processed before the download (a failed download would never be retried); storing only visible text (would lose spoiler-hidden links).
- **Not verified:** live Discord DOM (see the history-reader entry) and live pixeldrain; both are faked in tests. Passwords for password-protected archives found in this flow are not wired in yet.
- **Verify:** `tests/test_discord_pixeldrain_links.py`, `tests/test_discord_history.py`.

## 2026-10-17 - Standalone migration script (migrate_library_data.py)
- **Problem:** existing libraries have their history scattered over per-folder `.folder_log.json` files, the compressor's `library_log.jsonl`, logs the old compressor *parked* away from the downloader, and Pize manifests. New code reads the shared DB, so those need converting, and the user wanted it outside the menu, for all libraries, and safe.
- **Decision:** `migrate.sh` / `migrate.bat` run `scripts/migrate_library_data.py <library-root>... [--apply] [--report file.json]`. Dry run is the default and writes nothing (not even the DB or the app registry). Apply imports run records (deduplicated on folder + full record, so it is idempotent and `folder_log.read()` never shows a record twice), compressor `compressed` records as `files` identity rows, Pize manifest links as `pixeldrain_links` (its packages/posts are kept verbatim in `tool_data` until the plugin moves over), and registers the library in the app DB. One transaction per library, so an interrupt changes nothing. Legacy files are never moved, deleted or edited (tests compare checksums before/after). Odd things are reported, not guessed: nested `.library-data` folders (they would shadow the root), unreadable JSON, compressor records whose output file is missing.
- **Real data check:** a dry run against `/media/SSD/99DM` (read-only) found 766 parked per-folder logs the downloader could not see, 559 compressor records, and would import 1539 run records and 883 file-identity rows with no problems flagged.
- **Not covered:** `action_log` undo journals (`.last_action*.json`) stay as files (follow-up); `.manual` markers and drift are the next step; the downloader's own `.folder_log.json` files are imported but remain, so removing them is a manual choice.
- **Verify:** `tests/test_migrate_library_data.py`; run `./migrate.sh <root>` for the report.
